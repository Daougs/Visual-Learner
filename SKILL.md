# Visual Learner

Turn "I want to learn X" into a researched course book plus a series of narrated, beautifully animated explainer videos released **one lesson per day** on a schedule. Every lesson ships four ways: a chapter in the course book (a living doc), an **audio file (MP3)**, a **video file (MP4)**, and a scene in one interactive player page (a published Artifact).

**Nothing is premade.** This skill does not ship scripts, templates, models or example files, and no file in a build folder, kit or earlier session may be assumed to exist. You, the model, write and run every piece yourself: the speech engine, the scene renderer, the video recorder and the layout checker. The recipes below tell you what each piece must do and give the key code. If a file this skill names is missing, that is expected: create it. Never stop at "the build kit is not installed" and never hand the learner a plan in place of the finished audio and video.

## Ground rules

- **Quality and knowledge first, cost second.** Use extended web search, open and read primary sources, verify every number, get a fresh-eyes review of the outline, and never shorten a lesson to save tokens.
- **Facts come from research, not memory.** Every rate, price, law, date and statistic is looked up, read on the source page, cited and dated "as of". Anything unsourced is labelled approximate or general knowledge. Say when a source is secondary.
- **Pitch to the learner.** Define each new term in plain words at first use, give a line of intuition or a tiny worked example, and link back to the lesson that introduced earlier terms.
- **Video and book agree.** Every section, table, worked example and new term in the chapter appears on screen and in the narration, using only the figures in the book.
- **Never fake it.** No invented quotes, people or sources. Worked examples use clearly made-up names and say so.
- **Deliver the files.** A lesson is finished only when its MP3 and MP4 exist, play, and have matching durations.
- **One video per day.** Release exactly one lesson per day unless the learner asks otherwise. Lessons may be built ahead of time but are released on the schedule (Phase 7 is required, not optional).
- **Beautifully animated.** The video must feel designed, not like slides (see 5.6).

## Phase 1 - Intake

Use AskUserQuestion (skip and state defaults if unattended):

1. Topic, goal and what the learner already knows.
2. Minutes per lesson (default about 10).
3. Complexity: Beginner, Intermediate, Advanced or Beginner-to-advanced. Always ask.
4. Time frame to finish the course. Always ask. With lesson length it sets the lesson count.
5. If more than one video: "What time should the task run?", plus time zone and days.
6. Region or context when it matters (currency, law, tax), and narrator voice (default Kokoro `af_heart`).

If the learner asks for a structure (for example "global first, then country X"), build the parts in exactly that order and label each lesson with its part.

## Phase 2 - Research

Research before fixing an outline. Map the concepts, their dependencies, common misconceptions, and what the learner must be able to do at the end. For anything current or regional use WebSearch in extended mode and fetch the pages you take facts from; keep a source list with URLs and as-of dates. Find the numbers for worked examples and check each twice. Ask a subagent to review the draft outline cold: what is missing, wrong or out of order for this level?

## Phase 3 - Design the course

1. Lessons = days in the time frame (one per day), each about 150 spoken words a minute (10 minutes is roughly 1,300-1,500 words). In practice narration runs a little under target; say so honestly in the final message.
2. Group into parts (foundations, core skills, application). The last lesson is a set of scenario problems that combine everything, each posed, paused on for three seconds, then solved step by step.
3. Write the release schedule (date to lesson numbers). Show outline and schedule and get a yes before writing the book (skip if unattended).

## Phase 4 - The course book

Create a doc with Claude Docs (load the docs skill or guide first): title, byline, "How to use this book", one section per lesson, glossary, cheat sheet, sources. Plant the outline as pending blocks first, then fill one section per call. Chapter style: bold definitions at first use, intuition lines, back-links ("Day 3"), worked examples step by step, "New words" (about 8-10 terms) and a Practice checklist. Add a source line near every sourced number and flag made-up examples. Add a Release schedule table if lessons are released over time. Re-read the finished book once for consistency with the videos.

## Phase 5 - Build the pipeline yourself

Work in a build folder (for example `build/` with `out/` beside it). Create these pieces, in this order, testing each on one short lesson before running all of them.

### 5.1 Probe the machine

Check `python3`, `ffmpeg` (needs libx264 and libmp3lame), Playwright with Chromium, and CPU count. Install Python packages with `pip install --break-system-packages kokoro-onnx soundfile numpy` (Playwright and Chromium are usually pre-installed: do not reinstall). Network goes through an allowlist: Hugging Face is typically blocked while GitHub release downloads work. If a download is refused, say so and ask the learner to attach the file; do not retry other routes.

### 5.2 Get a local voice (Kokoro, CPU)

```bash
curl -L -o kokoro-v1.0.onnx https://github.com/thewh1teagle/kokoro-onnx/releases/download/model-files-v1.0/kokoro-v1.0.onnx
curl -L -o voices.bin       https://github.com/thewh1teagle/kokoro-onnx/releases/download/model-files-v1.0/voices-v1.0.bin
```

Confirm both files are tens of MB (an HTML error page is a failed download). Use `Kokoro(model, voices).create(text, voice="af_heart", speed=1.0, lang="en-us")`, which returns `(float32 samples, 24000)`. CPU synthesis runs a little slower than real time, so start long builds with `run_in_background` (never `nohup`; foreground sleeps are blocked, so wait with a bounded until-loop) and build lessons two at a time at most.

If the learner prefers another engine or an approved text-to-speech connector is available you may use it instead, but still produce one MP3 per lesson plus per-sentence start times so scenes stay synced.

### 5.3 Speech normaliser (`lexicon.py`)

TTS misreads written forms, so write a `spoken(text)` function that runs before synthesis and a `WORDS` dictionary you extend for the subject. At minimum: strip markdown bold markers; currency amounts to words (the rupee symbol or `Rs 5 crore`, `$36B` to "36 billion dollars"); `%` to "percent"; multiplication signs to "times"; numeric ranges (`10-12`) to "10 to 12"; spell acronyms the voice mangles (letter by letter with spaces such as "I R R", or a phonetic respelling such as "moik" for MOIC); regional units (lakh, crore). In lesson scripts also spell numbers for speech where it helps ("one over five", "to the power five"). Listen to or transcribe a sample and fix every misreading before the full build.

### 5.4 Lesson scripts as data (`lessons/dayN.py`)

Each lesson is a dict: `n`, `part`, `title`, `words` (term, meaning), `practice`, and `scenes`. A scene is `{title, cap, say, vis}` and, for problems, `hold` (seconds to pause) and `say2` (the answer narration). Plan 13-18 scenes per lesson: opening, concept scenes, a worked example built from numbers that appear on screen, New words, Practice and what is next. Visual types to implement: `title`, `bullets`, `table`, `bars` (horizontal), `cols` (vertical), `counter`, `flow`, `steps` (label and value lines, one highlighted), `split`, `line` (SVG curve, label what is illustrative), `stacks` (stacked bars), `words`, `problem` (question lines, countdown, answer lines). Narration is warm and conversational, one idea per sentence, with figures that match the visuals exactly. Sources go in `cap`.

### 5.5 Audio engine (`engine.py`)

For each scene: split `say` into sentences, synthesise each sentence separately with `spoken(sentence)`, cache every sentence as `.npy` keyed by a hash of voice, speed and spoken text (so a one-word edit re-synthesises one sentence), join with 0.22 s gaps, add 0.45 s of silence before and 0.8 s after the scene. For `hold` scenes insert the hold seconds of silence between `say` and `say2`. Record, per scene, its start time, duration, the start time of every sentence, and `rv`, the reveal time of each on-screen item: spread items across sentences (item i appears with sentence `int(i*n_sentences/n_items)`, staggered by 0.45 s inside one sentence), or follow an explicit sentence index per item if the script gives one. Write `out/dayN/scenes.json` and encode the joined audio with `ffmpeg -ac 1 -c:a libmp3lame -b:a 56k out/dayN/dayN.mp3`. Print minutes and spoken words; if a lesson overshoots the agreed length by more than about 10%, trim narration.

### 5.6 One stage, two uses (`template.html`)

Write a single HTML file that is both the interactive player and the video renderer. It contains a dark fixed 1280x720 stage and a deterministic function `draw(t, lessonIndex)` that renders any frame from the scene data alone: no timers, no CSS transitions, no randomness. Fades and counters are computed from `t` minus the item's reveal time. Expose `window.draw` and `window.stageHTML()`. The lesson JSON is injected where the template has a `/*__DATA__*/[]` placeholder. Add `?render=1` mode that hides player chrome and shows only the stage. Use large type (video is watched on phones), centred titles, a progress bar quantised to whole pixels (so static scenes produce identical frames), the caption at the foot and the part label at the top.

Player mode (for the Artifact): tabs per lesson or part, play and pause, a seek bar, speed control, a scene list, and the narration text for the current scene. Sound starts only after a click. Audio is referenced by relative paths `audio/dayN.mp3`. Follow the Artifact design rules (a `<title>` of 2-4 words, theme tokens for light and dark chrome, mobile-friendly layout, no download links).

**Make it beautiful.** Compute every motion from `t` with easing (ease-out cubic for entrances, ease-in-out for moves); never snap or pop.
- Entrances: each item slides up 16-24 px and fades in over 0.5-0.7 s at its reveal time, staggered; the highlighted item gets an accent sweep and a brief scale pulse.
- Numbers: counters roll with easing; bars grow from zero; stacked bars fill segment by segment; curves draw themselves with a stroke-dash reveal; table rows appear one by one with the active row tinted.
- Scene transitions: a 0.4 s cross-fade with a slight slide or scale, and titles that glide into the header position.
- Continuous life: a subtle deterministic background drift or vignette and a smooth progress bar so no frame looks frozen. Never leave a long scene static: if narration runs over 8 seconds, reveal something new every few seconds.
- Design: restrained palette (dark background, one accent, one second colour), generous spacing, large type (23-30 px body on the 1280 stage), consistent grid, simple SVG shapes or arrows where they explain.

A `make_player.py` merges every `out/day*/scenes.json` into the template twice: `out/player.html` for the Artifact and `out/render.html` for Chromium.

### 5.7 Layout check (`check.py`)

For each scene, call `draw(sceneEnd, idx)` in Playwright, screenshot to `out/shots/dayN_scene_KK.png`, and print a warning when any element's bounding box leaves the stage or overlaps its neighbour. Build a contact sheet per lesson, look at it, and fix overflow (shorten labels, fewer items, smaller type) before rendering. Always look at stacked bars, curves and problem scenes, which overflow first.

### 5.8 Video recorder (`record.py`)

Do not screen-record in real time. Step the page frame by frame:

```python
ff = subprocess.Popen(["ffmpeg","-y","-loglevel","error","-f","image2pipe","-framerate",str(fps),"-c:v","mjpeg","-i","-",
    "-i",mp3,"-c:v","libx264","-preset","veryfast","-crf","23","-pix_fmt","yuv420p","-r",str(fps),
    "-c:a","aac","-b:a","96k","-shortest","-movflags","+faststart",mp4], stdin=subprocess.PIPE)
with sync_playwright() as p:
    pg = p.chromium.launch().new_page(viewport={"width":1280,"height":720}, device_scale_factor=1)
    pg.goto("file://"+render_html+"?render=1"); pg.wait_for_function("window.draw !== undefined")
    for i in range(int(duration*fps)):
        pg.evaluate("([t,k]) => window.draw(t,k)", [i/fps, idx])
        key = md5(pg.evaluate("window.stageHTML()"))
        if key != last_key: last_img = pg.screenshot(type="jpeg", quality=90); last_key = key
        ff.stdin.write(last_img)
```

Use 24-30 fps for smooth motion (15 fps only for near-static scenes) and 1280x720. Frames whose stage HTML is identical reuse the last screenshot; if you add continuous background motion, key the dedupe on a coarser time step or drop it, and expect longer renders. Run at most two renders at once on a 2-core machine, in the background, after all audio exists.

### 5.9 Verify

`ffprobe` every MP3 and MP4: durations within about 0.5 s of each other, video 1280x720 with an audio stream. Extract one frame near the start and one near the end of each MP4 and look at them. Fix before delivery.

## Phase 6 - Publish

1. Run `make_player.py`, then publish `out/player.html` with the Artifact tool, attaching `audio/dayN.mp3` for every lesson through `files`; a short title such as "<Topic> 101", icon "video", one-sentence description. Do not paste the URL in the reply; the card carries it.
2. **Also attach every finished MP4 as `video/dayN.mp4`** to the same artifact (binary files up to 15 MB each, at most 64 MB per publish, so publish a few MP4s at a time to the same `url`). The artifact is the durable store scheduled runs download from, because each scheduled run starts in a fresh session where your build folder no longer exists.
3. Send the MP4 (video only) of any lesson released today with SendUserFile.
4. Add a "Listen and watch" line with the player link to the book.

## Phase 7 - Schedule the daily lessons (required)

Create the schedule with `create_trigger` (load it with ToolSearch; never local cron tools, which die with the session). One lesson per day:

- Cron in the learner's zone, bounded to exactly the release dates so no self-disable is needed, for example `CRON_TZ=Asia/Kolkata 0 7 14-20 11 *` for 7:00 AM on 14-20 November. For spans across months use one task per month. If today's delivery time has already passed, send lesson 1 now in this session and start the schedule with lesson 2 (or ask the learner).
- The prompt is standalone and complete: how to compute today's lesson number from the date, the player Artifact URL, instructions to `Artifact read` `video/dayN.mp4`, send that single MP4 with SendUserFile (no audio file, no other attachments), then one short SendUserMessage (title, one sentence, a reminder of the Practice checklist, a closing note on the last day), the lesson titles, and "do not rebuild anything; if the video cannot be read, say so and link the player".
- Only if the artifact cannot hold the videos, write the prompt to rebuild that day's lesson by following 5.1-5.9 of this skill.
- Tell the learner which approval setting the task got, and that they can switch it to automatic approval in its settings if runs will ask.

## Final message

Short: the course book link, lesson count and parts, what files exist (one MP3 and one MP4 per lesson, one player), honest notes (lengths versus target, secondary sources, uncertain rules, made-up examples), and the schedule (time, zone, first and last dates).
